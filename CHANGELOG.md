# Changelog

Every change to the global CLAUDE.md, an agent, or a skill gets an entry here, newest first. Record the *why* — the git diff already shows the what.

## 2026-10-05

- **followup, doc-sync, doc-model, milestone, implement, impl-plan, global, repo** — The ledger becomes one file per entry (`docs/fu/FU-NNN.md`) with flat front matter (`status / kind / areas / files / revisit / origin`), and `docs/follow-ups.md` becomes an index generated by `scripts/fu-index.ps1`, for the user only. In project B's M12 run the single 125 KB ledger was read 8 times just to land the milestone, and every agent that scanned "the index for overlapping Areas" paid for the whole file. Agents now grep the front matter. The new `files:` field lets a work package find its entries from the files it owns rather than by guessing at Area words. The index stays because Emilio wants a one-line view of every follow-up, like the plan gives for milestones. It is deterministic (no dates), so regenerating it never makes a diff on its own. `scripts/fu-migrate.ps1` converts a legacy ledger (in-ledger links become sibling-file links, the effective Revisit when moves to front matter, `files:` comes from backticked paths in Impacts that exist on disk). The generated rows keep the old `#fu-nnn` anchors, so existing links still land. Legacy ledgers keep working through `reference/legacy-ledger.md`. The scripts are PowerShell 7, at Emilio's choice.
- **repo** — Renamed `agent-stuff` to `claude-skills` in the README, `tests.md` and this changelog, to match the GitHub repo.

## 2026-10-01

- **repo** — Adds three scripts so checking a change stops depending on memory and typing. `scripts/lint.sh` checks the authoring conventions and cross-file contracts that need no Claude run (names match paths, every agent has a color, reviewers read-only, writing agents on sonnet, `${CLAUDE_SKILL_DIR}` paths exist, the reviewer roster, a coverage row per skill) and fails on tracked files matching an untracked `.lint-deny` — the private project names were removed by hand once and nothing stopped them coming back. `scripts/smoke.sh <n>` starts a smoke test: the model choice (recorded, since a cheaper model is a different test), the test's section as guidance, the scratch folder for Test 1, then an interactive session on the test's first prompt. A fully scripted run was rejected: the skills stop to ask questions, and half the checkboxes are about how Claude behaved, which needs a person in the session. `scripts/check-test.sh <n>` checks what Tests 1 and 5 leave on disk and prints the run-log row. The scripts are marked executable in git; `sync.sh` had been committed without the bit, so `scripts/sync.sh` would not run directly on Linux or macOS.
- **repo** — Prepared for sharing and for use on a second machine. Adds `README.md` (what each piece is, the plan → milestone → implement flow, how to try the skills project-locally) — until now the only entry point was `CLAUDE.md`, which is written for Claude — and an MIT `LICENSE`. The private projects these skills were distilled from are called projects A, B and C from here on, in this changelog, the global CLAUDE.md and `/walkthrough`'s reply reference; the global file drops its two pointers to a worked example in one of them. Tests 3, 4 and Test 9's status check run against those repos, so they moved to an untracked `tests.local.md`, and Test 11 uses placeholders. The run log gains a Model column, since a pass on a cheaper model doesn't carry over. History restarts from a single commit: the diffs behind the entries below are no longer in git, so the entries are the record.
- **repo** — `scripts/sync.sh apply` and `pull` skip the global CLAUDE.md unless `--global` is passed. On a fresh clone every repo file is newer than the live copy, so a plain `apply` replaced that machine's `~/.claude/CLAUDE.md` with this one, and `pull` could copy another machine's global file into the repo. `status` marks the row `[--global]`.
- **implement** — With no "Agents" section in the global or project CLAUDE.md, preflight falls back to the generic `reviewer` agent and says so in the run plan, or stops and asks if that isn't installed. The rule used to assume this repo's global CLAUDE.md was deployed, which no longer holds once `apply` skips it. Test 5 gains the check.
- **global** — When Emilio asks to understand a large document or what a whole repo does and the full answer would run well past a screen, give a short overview and offer `/walkthrough tour …` once, instead of one long explanation. Scoped like the 5+-points rule: main conversation only, not subagent reports, not mid-skill, not after he declines; small docs and specific questions just get answered.
- **walkthrough** — Adds tour mode: `/walkthrough tour [<file|dir|topic>] [goal]` is an information-only guided walk through a large document or a repo — an outline of stops, each explained briefly from the real source, with a picker to continue, expand (sub-stops for big ones), skip for later, or ask a question on the spot. Emilio wants to absorb large material step by step with the same accept/skip/expand/ask rhythm as decision walkthroughs; the old "understand" mode assumed a list already existed and had no way to build one from a document or codebase. Kept in the same skill because the loop (progress header, picker, nothing dropped, resume) is identical and real sessions mix explaining with deciding — the M7 review started with "explain how a subsystem works" before any decision. Tours decide nothing and edit nothing: chat-only unless he asks to save notes (which then become a resumable log), decisions that surface are parked for the end, and repo exploration is two-phase so a large repo isn't read in full before he's picked a scope. Guarded against over-triggering: a plain "explain X" or "walk me through this function" still gets a normal answer, and a file with nothing left to decide offers a tour instead of starting one. `tests.md` gains Test 11.
- **walkthrough, milestone, implement, followup, doc-sync, global, repo** — Pre-deploy review fixes for `/walkthrough`. It now writes milestone Reviewer decisions only into `proposed`/`approved` docs (an approved doc is pointed back to `/milestone refresh` for re-approval; in-progress, landed and frozen-spec docs get log-only), never touches a Status or gate line, records into draft vs approved plans per the doc model, and returns control to `/milestone refresh` or `/impl-plan` when they hand off — refresh then asks about any design question left open before approving. The global 5+-points offer is scoped to decisions asked of Emilio in the main conversation: not subagent reports, not findings Claude is about to fix, not `/implement` runs. Logs carry a stub per point so a chat-sourced walkthrough survives a new session; picker respects AskUserQuestion's limits (ID as header, ≤3 alternatives + Tell me more, plain-text fallback); plan mode writes nothing; asks before creating a log for non-project chats or where `docs/` doesn't exist; unique log names; resume lists multiple unfinished logs and re-verifies a changed source; deferred points use `Kind: deferred` with a warning against self-blocking milestone ids. Test 10 runs on a throwaway branch and covers the hand-off, plan mode, chat-sourced resume and the negative proactive case.
- **repo** — `tests.md` gains Test 10 for `/walkthrough` (agenda, reply paths incl. a new idea mid-review, decisions written as they're made, completeness check, resume, and the proactive 5+-points offer) plus coverage rows.
- **global** — When a response would hand Emilio 5+ decisions, questions or review findings, end with a compact recommendation table and offer `/walkthrough` instead of a wall of questions. Long multi-question responses are where items get skipped and forgotten; by project B's M10/M12 he was already preferring a summary table with the hard calls flagged.
- **milestone, impl-plan, doc-sync, repo** — Wire `/walkthrough` into the existing flows: `/milestone refresh` hands approval to a walkthrough when more than four design questions are open (the batch-of-four picker gets unwieldy beyond that), `/impl-plan` offers one for leftover ask-user decisions, and doc-sync never edits walkthrough logs in `docs/reviews/`. Repo contracts list walkthrough as a ledger writer (via `/followup`) and as a writer of milestone Reviewer decisions.
- **walkthrough** (new) — `/walkthrough [<file> | <file>#<section> | resume] [--only …]` turns any list — an agent's 10 open questions, a document review, a fresh plan — into a tracked agenda and works through it one point at a time: a short brief (situation, options with tradeoffs, recommendation, exact proposed text when a document changes) plus a picker (Recommended / alternative / Tell me more / Defer; free text always works). Emilio struggled to answer long responses point by point and sometimes forgot items. Distilled from his two best sessions: the project B M7 review (question by question, recommendation + flagged judgment call, follow-ups for anything to revisit) — minus its friction (hidden decision log, 900–1,400-word points, no progress marker, no completeness guarantee) — and a claude.ai spec review (exact replacement text per point, new ideas folded in mid-review with later points reworked, covered points absorbed under stable IDs, concede-or-guardrail on user ideas, scope bins, checkpoint applies with "approvals since last apply", and reporting undiscussed additions after applying). Decisions go into the source's decisions section as they're made plus an in-repo log at `docs/reviews/`, shown every time, so a walkthrough survives a break and resumes.
- **repo** — Adds `tests.md`, a manual smoke-test runbook for the planning and implementation skills (9 tests: greenfield plan → milestones, refresh, real-doc regeneration on project A, legacy refresh and convention detection, guided `/implement`, mode switch, swarm with forced interruption, merge gate, deferred criteria / user checks / read-only status). Prompt files have no automated suite, and without a fixed runbook each check would be improvised and incomparable between skill versions. A coverage table maps each skill/agent to its tests so a change knows what to rerun; a run log records results against the deployed `claude-skills` commit. CLAUDE.md's workflow gains a smoke-test step and the rule to update tests alongside behavior changes.
- **implement** — `/implement <id>` now checks that milestone's dependencies (landed or awaiting a user check) and stops with the blockers otherwise; only ranges checked this before, so "let's start implementing M1" with M0 unbuilt would have started anyway. Found while writing the implementation test runbook.
- **implement, milestone, doc-sync, followup, repo** — Pre-deploy review fixes. Git-history safety: a reverted merge is never marked landed (resume and doc-sync drift repair skip merges with a later Revert, and `Stub …` commits); a retry after a revert reverts the revert instead of a no-op `git merge` of the old branch; blocked branches are kept and listed instead of pushing toward `branch -D`, which is now explicitly forbidden along with `worktree remove --force`, `clean` and discarding uncommitted work; allowed-tools narrowed so those rules don't rest on prose alone (no blanket `git -C *`). Resume: a half-done merge is aborted first, merged-but-uncleaned worktrees are only cleaned, empty means no commits *and* clean, live workers are never salvaged. `awaiting user check` is wired end to end — `/implement` re-offers the checks and lands on confirmation, `/milestone next` and the generated plan/index text no longer stall on it. WP markers `☑ landed` / `⛔ blocked` defined; blocked WPs aren't retried; staleness excludes the doc's own approval commits (no refresh churn); every WP is implicitly After `.0`; re-deferral of a ledger entry is an Update bullet. doc-sync never creates entries when `/implement` invokes it. The repo CLAUDE.md contracts (ledger Kind fields, `/implement` in the plan/milestone contract, its invocation gate) were changed in this series without their own entry — recorded here.
- **global** — The Documentation Workflow rule names `/implement` (guided by default) and `/milestone mode` for switching to the agent swarm, and makes recording compromise/revisit-later decisions as `/followup` entries a standing behavior — Emilio asked for it explicitly in several project B sessions ("if any proposed decision had a compromise or I might want to revisit it create a followup").
- **implement** (new) — `/implement [next | <id> | <id>..<id> | all | status] [--agents N]` implements milestones from their docs, guided (one work package at a time, pause after each — Emilio's project B flow, kept consistent instead of loosening over time) or swarm (worktree agents, coordinator merges). Replaces the ad-hoc "implement all milestones, choose a solution on your own and document it" prompts. Every rule traces to a failure in project A's swarm run: 7 of 11 agents died on session limits before committing → workers commit WIP early and commit their report file, and state is derived from docs/git/worktrees so re-running resumes; every agent assigned the same FU id → only the coordinator numbers follow-ups, workers use `FU-TBD-*` placeholders; docs synced 5 times across 19 merges → doc-sync after every merge; a coordinator note was merged into code → merge gates; 19 worktrees left behind (7 locked) → cleanup with unlock; a deferred joint test vanished → deferred criteria become ledger entries that block the owning milestone. Default cap of 4 agents limits rate-limit burn. Model-invocable so "let's start implementing M3" routes here, but self-invoked it only runs guided on one milestone and asks first. `/milestone refresh --autonomous` added for mid-run approvals.
- **doc-sync** — Ready for per-merge syncing by `/implement`: takes the merge sha and WP report as evidence, repairs drift (a merged WP not yet marked landed gets synced even outside the given range — project A's M1a stayed "not started" after merging, and M6a's as-built had to be backfilled), lists concurrent WPs in status, uses `awaiting user check` for milestones whose only open criteria are interactive, refuses to land a milestone while an open ledger entry names it in Revisit when, and sets the plan `implemented` only with Definition-of-done evidence (project A's M7 claimed whole-project DoD while a deferred criterion was still open). Project CLAUDE.md status lines become a named surface — project A's still says "Design-only. No code exists yet". Never claims review results it wasn't given (a project B as-built falsely said "no review defects").
- **milestone** — `/milestone mode <guided|swarm> [<id> | from <id> | all]` switches how milestones get implemented. Emilio's usual pattern is guiding the core milestones and handing the rest to agents once he's comfortable (project A: guided M0, then the whole rest in one swarm run), and he sometimes changes his mind before starting. Switching to swarm re-runs the swarm-readiness check — including against code that landed since the doc was written — and refuses targets that would let parallel work packages collide, rather than discovering it as merge conflicts mid-run. Only the Execution field and the Refresh log change; status and history are untouched.
- **impl-plan, milestone** — Execution mode becomes a per-milestone field (`Execution: guided | swarm`, plan-level default) instead of a plan-wide choice that changed how docs were written. Milestone docs are now always swarm-ready: every work package declares `After:`, file ownership is exclusive between unordered WPs, and `WP<n>.0` pre-edits shared hotspots (package refs, project files, registries). Emilio often guides the core milestones and later lets agents take over, or changes his mind before starting; with the old model that meant rewriting docs. The hotspot rule makes project A's ad-hoc "Prep wave-4 package references" commit a planned step — without it, 11 parallel agents conflicted in csproj files. Also: `in progress (awaiting user check)` status, the deferred-criterion rule, reserved fake names for not-implemented test exemplars (project A's tests broke twice when later WPs implemented the "unimplemented" example), and a swarm-readiness check in refresh.
- **followup** — Entries gain a **Kind** (`deferred` / `decision` / `compromise` / `limitation`) plus **Why accepted** and **Revisit when**, and new ledgers get a Kind column in the Index. Emilio asks for follow-ups on "any decision that had a compromise or I might want to revisit"; after an autonomous run he needs to filter for those rather than read every entry. Project B's ledger had already grown the same fields organically (11 "Why accepted", 7 "Revisit when"). A bare milestone id in Revisit when blocks that milestone from landing — project A silently dropped an M4a/M4b joint acceptance test that had been deferred "to the M6a gate". doc-sync and the doc model follow; doc-sync appends dated Update bullets instead of duplicate entries (project A had independent rediscoveries of the same finding).

## 2026-09-30

- **followup** — Ledger status wording is now `done (<sha> or PR #N, date)`, matching what projects A, B and C actually write (all use commit SHAs, none used the old `done (PR #N)`). New entries get an explicit `<a id="fu-nnn">` anchor so links survive title edits, and the skill spells out the link form from other docs — project A's milestone docs had broken `./follow-ups.md` links from `docs/milestones/`. Origin names the plan section or milestone when invoked by the planning skills.
- **impl-plan** (new) — `/impl-plan <what to build>` writes the master implementation plan. Codifies the plan format used across projects A, B and C so results stop varying with prompt wording: gated milestones, Chosen/Rejected decisions, `[VERIFY]` + assumption register, annotated layout, one-line status. Adds a fresh-context critique pass (project A's separate "plan review" commit caught real gaps) and hands off to `/milestone all`. User-only (`disable-model-invocation`) because it writes many files and asks several questions. `reference/doc-model.md` is the canonical doc model both skills share.
- **milestone** (new) — `/milestone [all|next|<id>|refresh <id>]` splits the plan into milestone docs: design questions (Proposal/Alternative → Reviewer decisions) plus commit-sized work packages with exclusive file ownership, acceptance checklist, ledger reconciliation, append-only As-built record. Writes all docs up front by default (Emilio wants the whole picture to review); `refresh` re-validates a pre-written doc against everything since its `Written against` sha before implementation — addressing project C's lesson that up-front docs go stale. Model-invocable so `/impl-plan` can chain into it and Claude can refresh before implementing. Drafts in parallel subagents from 4 docs up, with a main-agent skeleton and consistency pass to keep them coherent.
- **doc-sync** — Learns the plan/milestone model: discovers `*IMPLEMENTATION*`/`*roadmap*` plans and `docs/milestones/` (it previously missed project A's and project B's plans entirely), ticks milestone criteria only with evidence, fills the As-built record only once all criteria pass, owns the in-progress/landed/implemented status transitions (doc-model's "Who changes what" table), never lands a milestone with an unmet criterion on its own, treats landed docs as frozen, and reports stale pre-written docs as `needs /milestone refresh <id>` instead of editing them. Keeps the plan to one status line per milestone (project C's plan had grown narrative landing entries). Ledger status wording matches followup.
- **global** — Documentation Workflow rule now names plan + milestone docs as doc surfaces, and says to run `/milestone refresh <id>` before implementing a pre-written milestone.
- **repo** — CLAUDE.md gains the "Plan/milestone docs" cross-file contract and the updated ledger contract; authoring conventions for `disable-model-invocation` and hard-rules-first skills.
- **repo** — Imported the live config from `~/.claude` as the baseline: global `CLAUDE.md`, 9 agents (`csharp-reviewer`, `doc-sync`, `docs-writer`, `python-reviewer`, `react-reviewer`, `refactorer`, `reviewer`, `test-writer`, `vulkan-reviewer`), and the `followup` skill.
