# doc-sync: plan and milestone docs

Read by the `doc-sync` agent in projects planned with `/impl-plan` + `/milestone`. Which transitions are doc-sync's is doc-model's "Who changes what" (same folder); this is how to make them. An older single-file milestone doc is landed history — never edit it.

- **Progress markers** — the milestone's `in progress (…)` line, the gate and plan header `in progress`, and the WP markers in the overview's table (`☑ landed`, `⛔ blocked (FU-NNN — <why>)`). When `/implement` invokes you it has already written them: leave them alone. Invoked for ad-hoc work, write them yourself.
- **Active milestone** (the one the commit range worked on):
  - Tick acceptance criteria only with evidence: `- [x] <criterion> — <TestClass.Method / command → output>`. Unverifiable → leave `[ ]` with a **bold reason**.
  - **Deviations:** append to `as-built.md` under `## Deviations` one `### WP<id> — \`<sha>\` (<date>)` entry for each WP that differed from its WP file or the overview — nothing for a WP built as written, and never a restatement of a decision (the overview's `D<n>` bullet holds it) or a follow-up (the ledger holds it). A guided milestone's WP commits carry a `Deviation:` line in their body when they differed (`git log --format=%B <range>`); a swarm WP's report has them. A deviation from a contract another milestone owns also gets a dated back-note in the owner's `as-built.md`.
  - Code complete with only interactive criteria left ("run the demo and see it spin"): set `in progress (awaiting user check)` and report the exact command and what to look for under "could not fix". When the invoker later passes the user's confirmation, tick those criteria with the quote as evidence and land the milestone.
  - **Landing is blocked** while any open ledger entry's `revisit:` names this milestone — report those entries instead.
  - **A deferred criterion does not block landing:** one the invoker moved to a later milestone (an open `kind: deferred` entry whose `revisit:` names that *later* milestone) stays `- [ ]` with a **bold reason** linking the entry (`../../fu/FU-NNN.md` from a milestone folder), and counts as settled.
  - Once **all** criteria pass: fill `as-built.md`'s `## Landing record` — Landed (date, sha) and Notes for the next milestone; the evidence is already on the ticked criteria — and set the doc's `☑ landed (YYYY-MM-DD, <sha>)`. Never fill it speculatively or partially. If a criterion is still unmet (e.g. an interactive check the user hasn't confirmed), don't land it — report it under "could not fix"; landing with an outstanding criterion is the user's decision, recorded as a Status qualifier and in the landing record.
- **Landed docs are frozen.** Later corrections are new dated entries (`### YYYY-MM-DD — <event>`) in the as-built record; never edit the body.
- **Pre-written future docs:** don't edit them. If landed work makes one stale (changed contract, renamed file, answered question), report `needs /milestone refresh <id>` under "could not fix".
- **Missing doc:** never create milestone docs — report the gap and suggest `/milestone <id>`.
- **Drift repair:** a `Merge <M> WPx.y …` commit (or a `(<M> WPx.y)` commit) whose WP has no landed marker gets it (when you weren't invoked by `/implement`) and its deviation note, if it has one, even if it predates the range you were given — **unless** a later `Revert "…"` commit undoes it, or it is a `Stub <M> WPx.y` commit; those are never landed.
- **The plan:** update only the header status (`implemented (date)` once every gate is landed **and** the plan's Definition of done has evidence **and** no open `deferred` entry names a landed milestone; `in progress — <ids> active` only for ad-hoc work), the gate's status line (`landed (date, <sha>)`), resolved `[VERIFY]` tags and assumption-register rows, and — only in a plan that has one — its `Last updated` line. No narrative in the plan — the as-built record holds it.
